## 1. Outcome

Batch 3 will make PostgreSQL the authoritative per-account source while preserving the existing immediate React mutation behavior and an explicit, non-destructive import route for the current browser snapshot.

After implementation:

1. the app resolves the cookie session before any private state renders;
2. the app loads and validates only the authenticated user's server snapshot;
3. a new account receives either an explicitly imported local snapshot or a fresh version-2 snapshot;
4. UI mutations stay immediate but persistence is serialized through one revision-aware queue;
5. `409`, session expiry, network failure, and unsupported schema fail visibly without silent overwrite;
6. `localStorage.lifeOsState` is never written or deleted and is read only by the import bridge;
7. theme/sidebar/scene remain browser-local preferences;
8. the first account can be created from a deliberate `?bootstrap=1` setup screen without Bootstrap CSS or a compiled token.

**VERIFIED current boundary:** the backend request owner is cookie-derived and state PUT accepts only `expected_revision`, literal schema version 2, and object payload (`apps/api/app/schemas/state.py:7-29`; `apps/api/app/routes/state.py:37-59`). Batch 3 sends no `user_id`.

## 2. Approved architecture proposed for sign-off

### 2.1 Root boot gates

`App` becomes the owner of the existing locale/theme state and renders this sequence:

```text
LifeLocaleContext.Provider
└── AuthProvider
    └── AuthGate
        ├── booting/error → neutral status/retry screen
        ├── anonymous     → LoginPage or ?bootstrap=1 setup mode
        └── authenticated → LifeDataProvider(user)
                              ├── loading/import/recovery gate
                              └── AppShell only after state acknowledgement
```

- Locale remains RU by default and is not newly persisted.
- Theme and paradise-scene preferences keep their current localStorage keys and behavior (`apps/web/src/App.jsx:70-184`).
- The route shell never sees `LifeDataContext=null` or a seed created before server resolution.
- StrictMode-safe async effects use generation/cleanup guards. Initial state creation is deduplicated by a module-scoped in-flight boot promise keyed by authenticated user ID, so the dev remount cannot issue two expected-revision-0 PUTs.

### 2.2 Authentication state

`AuthProvider` states are:

```text
booting → authenticated | anonymous | error
anonymous → authenticating → authenticated | anonymous(error)
authenticated → logging_out → anonymous
authenticated → expired → anonymous
```

- Boot calls `GET /api/v1/auth/me`.
- `401 not_authenticated` is an ordinary anonymous boot result; transport/5xx is a retryable boot error.
- Login errors stay generic because the server deliberately does not reveal unknown email vs wrong password.
- Logout immediately unmounts/clears the private provider and disposes its queue, then calls the idempotent server logout. A network failure is shown, but no private state remains rendered.
- A 401 from state load/save calls `expireSession()` and clears the same private boundary.
- Password and bootstrap-token values live only in form state for the request lifetime; they are cleared after completion and never logged/stored.

### 2.3 Bootstrap setup UX — owner-approved

- The setup form appears only when the URL has `?bootstrap=1`; it is not a public registration route.
- Fields: email, password, confirm password, bootstrap token.
- The token is manually pasted and never read from `import.meta.env`, bundled constants, localStorage, logs, or error telemetry.
- Success uses the returned cookie/session and continues directly into server-state initialization/import.
- `409 bootstrap_closed` switches to an “already initialized” message with a login action.
- `403` remains a generic invalid setup-token message.
- The ordinary login screen contains no signup link; a small setup affordance is shown only while the query parameter is present.
- Styling uses existing Life OS CSS tokens. No Bootstrap CSS/library/package is added.

### 2.4 API client and error mapping

All network traffic passes through `api/client.ts`:

- relative same-origin paths only;
- `credentials: "same-origin"`;
- JSON content type for body requests;
- 204 support;
- safe parsing of stable `{code,message}`, revision conflict, FastAPI validation details, HTML/empty failures, and network exceptions;
- no request/response body logging;
- optional `AbortSignal` for read requests.

`ApiError.status/code/details` is the sole typed HTTP failure contract. `NetworkError` is distinct from an HTTP error so UI never labels a server validation failure as “offline.”

### 2.5 State initialization and explicit legacy choice

`StateRepository.load()` maps only typed `404 state_not_initialized` to `null`; other 404/errors remain errors.

For an authenticated user with no server row:

1. read legacy local state exactly once;
2. if absent, automatically PUT a copied `buildInitialState()` with expected revision 0;
3. if valid legacy data exists, block route rendering and show preview with version, byte size, and counts for tasks/goals/transactions/medications/notes/activity;
4. “Import local data” migrates a deep copy and PUTs it with revision 0;
5. “Start fresh” PUTs `buildInitialState()` with revision 0;
6. neither choice changes/deletes `lifeOsState`;
7. only after a successful PUT, write a non-authoritative marker `lifeOsLegacyDecision:<user-id>` containing decision + acknowledged revision. The marker never suppresses a future prompt if the server again says no row.

Invalid JSON/storage-denied/newer-schema legacy data is surfaced as an import error with raw-download (when raw exists) and “start fresh”; it is never silently treated as absent.

### 2.6 Schema migration

Rename `migrate()` to exported `migrateStateCopy(input)` and make it pure:

- clone before any change;
- reject non-object/array input;
- reject missing/non-numeric version except the known legacy v1 form;
- migrate v1/<2 fields to exactly v2;
- accept v2 only after required top-level collection/object guards;
- reject `version > 2` before render/save;
- seed/migrate persisted habits as described in §2.10;
- never modify the server envelope payload or local parsed object in place.

### 2.7 Revision-aware synchronization coordinator

One `StateSyncCoordinator` instance exists per mounted authenticated provider.

Invariants:

- initial revision is the server-acknowledged revision;
- 500 ms trailing debounce preserves the current local feel;
- at most one PUT is in flight;
- pending payload is always the latest state object;
- mutation during a PUT produces one next PUT using the newly acknowledged revision;
- successful response is the only source of a new revision;
- no state PUT starts before hydration/initialization/import acknowledgement;
- 409 freezes writes and retains pending/in-memory payload;
- 401 expires auth and disposes the queue;
- network/5xx preserves pending state and exposes retry; no timer retry loop;
- retry occurs only on explicit action or browser `online` event and reuses the same expected revision;
- browser `beforeunload` warns while unsaved/offline/conflict/error state exists; it does not attempt an unreliable async flush;
- `dispose()` prevents late responses from mutating unmounted/account-switched state.

If a retry is ambiguous because the server committed but the response was lost, a 409 is still shown. The client does not compare-and-force or silently advance revision.

### 2.8 Conflict and recovery UX

On 409:

- existing UI remains visible with the unsaved in-memory winner candidate;
- all later writes are frozen/coalesced but not sent;
- SyncStatus offers “Export unsaved JSON” and “Reload server version”;
- reload is explicit and warns that unsaved changes will be discarded;
- reload performs GET, validates/migrates, replaces memory, resets coordinator revision/status, then resumes writes;
- there is no merge or force-overwrite button in PF-01.

On unsupported/corrupt server payload, route UI does not mount. Recovery offers retry/logout and raw response export only when safely available; it never PUTs a seed over an existing row.

### 2.9 Reset semantics

The existing “delete all data” control becomes a two-step confirmed data reset, not account deletion:

- disabled while load/conflict is unresolved;
- waits for any current PUT to settle, cancels queued debounce payload, and replaces with a fresh valid v2 seed using the latest acknowledged revision;
- on success replaces in-memory state and keeps the account/session;
- on failure retains the pre-reset in-memory state and shows the real sync error;
- never deletes a DB row, browser preferences, or legacy local snapshot.

The public context name `hardReset` is retained for caller compatibility but becomes `async` and revision-aware.

### 2.10 Habits persistence compatibility fix

This Plan includes the Discovery-recommended scoped fix because a global “saved” indicator would otherwise lie about habit toggles.

- `buildInitialState().habits` becomes the four shipped habits as an array with stable IDs and `titleKey` rather than localized stored names.
- `migrateStateCopy` converts missing/invalid `{}` habits to that seed; existing valid arrays are preserved, mapping legacy literal `name` as fallback.
- Add `toggleHabitToday(habitId, todayIndex)` to `LifeDataContext`; it toggles exactly one week cell without adding new streak/business calculations or activity-log entries.
- `HabitsPage` passes context habits and toggle callback to `HabitsGrid`.
- `HabitsGrid` becomes controlled for persisted mode; its existing empty-mode behavior remains.
- No add/delete habit feature is added; the existing inert “add habit” button remains out of scope.

## 7. State lifecycle and race matrix

| State/key | Writer | Reader | Clear/TTL | Restart/corrupt/double-tap/deploy race |
|---|---|---|---|---|
| Auth user | AuthProvider from me/login/bootstrap | App/Login/Settings | logout/401 clears memory; cookie TTL server-side | Restart calls me; stale response ignored by generation guard. |
| Password/bootstrap token | controlled form | one auth request | cleared after request/unmount | Never persisted/logged. |
| Server snapshot | coordinator/initial import/reset | LifeDataProvider/15 consumers | no deletion | Restart GET; newer/corrupt schema blocks; revision race freezes. |
| Acknowledged revision | coordinator | each PUT | reset from load/reload | Only server response advances it. |
| Pending payload | coordinator | retry/export/status | success/dispose/logout | Double mutation coalesces latest; never concurrent PUT. |
| `lifeOsState` | **no Batch 3 writer** | legacy bridge only | **never cleared** | Restart never auto-imports; every absent-row choice remains explicit. |
| legacy decision marker | post-ack import/fresh only | diagnostic only | no TTL | User-scoped; never overrides server 404 decision. |
| theme/sidebar/scene | existing App hooks | App/UI | existing remove behavior | Remains browser-local and survives login/logout. |
| habits | initial/migration/toggle context | HabitsGrid | reset only | Included in snapshot/revision like other domain keys. |
| sync phase/error | coordinator/provider | SyncStatus/Settings | new success/load/logout | Honest saved/offline/conflict/error labels. |

## 8. Invariants checklist

- **Multi-account isolation:** no frontend schema/body accepts or sends `user_id`; state only follows the server cookie session.
