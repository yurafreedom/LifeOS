### 3.4 Mutation timing

**VERIFIED (HEAD `102aea4`):** all domain mutations are synchronous React state updates. `mutate()` merges a patch and activity entry atomically (`LifeDataContext.jsx:202-215`); several flows use one custom `setStateRaw` pass for coupled changes (`:218-233`, `:277-307`, `:373-395`). Server persistence must remain transport-after-mutation and cannot make these callers await before the UI updates.

The required queue invariant is therefore:

```text
UI mutation → in-memory state changes immediately
            → debounce/coalesce latest payload
            → at most one PUT for acknowledged revision N
            → success records N+1
            → if state changed during request, send latest payload with N+1
            → 409/401/schema error stops further writes
```

No automatic 409 retry is safe: it would overwrite another device's winner.

## 5. Live API contract Batch 3 must consume

| Endpoint | Live response | Client implication |
|---|---|---|
| `POST /api/v1/auth/bootstrap` | 201 user + cookie; 403 bad token; 409 closed | No backend “is bootstrap open?” endpoint exists. UI exposure is an unresolved product decision. |
| `POST /api/v1/auth/login` | 200 user + cookie; generic 401 | Login UI cannot distinguish unknown account from wrong password. |
| `POST /api/v1/auth/logout` | idempotent 204 + clear cookie | Client must clear private in-memory state even if UI transitions after a network error. |
| `GET /api/v1/auth/me` | user or 401 | This is the boot/session authority. |
| `GET /api/v1/state` | envelope or typed 404 | 404 means definitely no row, not an empty `{}` payload. |
| `PUT /api/v1/state` | first 201/revision 1; later 200/N+1; stale 409/current revision | Repository owns the acknowledged revision and must never manufacture/retry a newer revision. |

## 10. Open decisions for Phase B

1. **Initial state:** recommend automatic first PUT of `buildInitialState()` only after an authenticated typed 404 and only when no legacy snapshot exists. This is safe because 404 proves no server row.
2. **Legacy choice:** recommend prompt with “import local data” and “start fresh”; both leave `lifeOsState` untouched, and either PUT must succeed before render.
3. **Bootstrap UX:** recommend a deliberate `?bootstrap` owner-only setup mode that requires manual token entry and disappears after 409; never compile the token. Alternative is documented CLI-only bootstrap.
4. **Conflict UX:** recommend freeze + “export unsaved JSON” + “reload server version”; no force overwrite and no automatic retry with `current_revision`.
5. **Network retry:** recommend no timer loop. Retry on browser `online` event and an explicit “retry” action while keeping one in-flight request.
6. **Reset:** recommend confirmed replacement with a fresh valid v2 seed at the acknowledged revision; no account deletion and no local-key deletion.
7. **Habits:** recommend including the minimal hoist/migration in Batch 3 because otherwise the UI can display “saved” while habit changes never enter the snapshot. This is a scope expansion requiring explicit sign-off.
8. **TypeScript:** recommend real TS gates (`typescript` plus ESLint TS support and `tsc --noEmit`) if retaining the approved `.ts` files. The lower-scope alternative is `.js` + JSDoc with no new dependencies.
9. **Local origin:** recommend adding `http://127.0.0.1:5173` to the example allowed origins while retaining localhost; this expands Batch 3 beyond frontend-only scope by one config line.
10. **Locale ownership:** recommend hoisting locale/provider above auth/data gates while preserving current default RU and no new locale persistence.

All ten decisions must be consolidated as sign-off items in Phase B; none may be silently selected during implementation.

## 13. Discovery conclusion

The approved direction is implementable on the live HEAD, but the Phase B Plan must close the ten decisions above and re-anchor every file/symbol to `102aea4`. The most important safety property is a three-gate boot sequence:

```text
authenticated user resolved
        ↓
server state resolved or explicit first-state choice acknowledged
        ↓
provider becomes writable and the route shell mounts
```

Opening writes before all three gates risks destroying the server winner or importing local private data into the wrong account.
