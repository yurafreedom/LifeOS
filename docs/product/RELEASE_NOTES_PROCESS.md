# JENKIN — как вести историю обновлений

Канонический источник один: [`apps/web/src/data/releaseNotes.json`](../../apps/web/src/data/releaseNotes.json).
Из него строятся страница приложения `#/updates` и корневой [`CHANGELOG.md`](../../CHANGELOG.md).
`CHANGELOG.md` вручную не редактируется. Схема и правила проверки —
[`apps/web/src/domain/releaseNotes.js`](../../apps/web/src/domain/releaseNotes.js).

## Версии: три разных понятия

- **Версия сборки** — `apps/web/package.json` → `version`. Показывается в «Настройки →
  о JENKIN» и в шапке `#/updates`. Сама по себе выпуском не является.
- **Выпуск** — запись `"status": "released"` с `"version": "MAJOR.MINOR.PATCH"` и
  реальной датой выпуска `"releasedOn": "YYYY-MM-DD"`.
- **Невыпущенное** — не более одной записи `"status": "unreleased"`, `"version": null`,
  `"releasedOn": null`; всегда первая в списке.

Дата коммита — не дата выпуска. Не придумывайте прошлых версий и дат.

## Схема записи (v1)

```json
{
  "id": "unreleased",                 // стабильный kebab-case id; у выпуска, например, "v0-2-0"
  "status": "unreleased",             // "unreleased" | "released"
  "version": null,                    // semver только у released
  "releasedOn": null,                 // реальная дата только у released
  "title":   { "ru": "…", "uk": "…" },
  "summary": { "ru": "…", "uk": "…" },
  "changes": {                        // группы необязательны, но непустые; порядок показа фиксирован
    "features": [ { "ru": "…", "uk": "…" } ],
    "improvements": [], "fixes": [], "security": [], "limitations": []
  },
  "technical": [ { "ru": "…", "uk": "…" } ],         // необязательно, под раскрытием
  "refs": [ { "kind": "commit", "value": "abc1234" } ] // необязательно; коммиты из этой сборки
}
```

Проверка отклоняет: пропущенный RU или UK текст, неизвестные поля и группы, версию
или дату у невыпущенной записи, выпуск без версии или реальной даты, больше одной
невыпущенной записи или не на первом месте, выпуски не по убыванию даты и версии,
повторяющиеся id, адреса почты, локальные пути и локальные адреса в тексте. Тесты
также требуют, чтобы RU и UK не совпадали дословно и чтобы каждый коммит из `refs`
был предком текущего `HEAD`.

## Шаги

1. **Во время разработки** добавляйте пользовательские изменения в запись
   `unreleased` (создайте её первой, если её нет) — на RU и UK, в подходящую группу.
   Пишите результат для пользователя («что теперь можно и что изменилось»), а не текст
   коммита. Внутренние детали — в `technical`.
2. Выполните в `apps/web`:
   ```bash
   npm run release-notes          # проверить источник и пересобрать CHANGELOG.md
   npm test                       # включает release-notes.test.jsx
   ```
   Закоммитьте `releaseNotes.json` и `CHANGELOG.md` вместе.
3. **Перед выпуском** перечитайте формулировки и проверьте, что каждая возможность
   действительно есть в выпускаемой сборке (функция в невлитой ветке — не в выпуске;
   отчёт о реализации — не доказательство включения).
4. **При выпуске** (решение владельца): поменяйте у записи `status` на `released`,
   задайте `id` (например, `v0-2-0`), `version` и фактическую дату `releasedOn`; при
   необходимости поднимите `version` в `apps/web/package.json` до той же версии;
   снова `npm run release-notes`. Новую запись `unreleased` создавайте, когда появятся
   следующие изменения.
5. **Прежние записи не удаляйте и не переписывайте** задним числом, кроме исправления
   опечаток и фактических ошибок.
6. **Не превращайте каждый коммит в запись.** Рефакторинг, тесты, отчёты и
   внутренние инструменты в пользовательские пункты не попадают (максимум — строка
   в `technical`).

Что нельзя публиковать: токены, ключи, почту аккаунтов, личные финансовые данные,
локальные пути, детали внутреннего QA, неподключённые интеграции как готовые,
утверждения, что проблема безопасности «полностью устранена». Заметки о безопасности
описывают последствия для пользователя без операционных подробностей.
