## 5. Database findings

### 5.1 Email uniqueness

**VERIFIED:** the Plan says case-insensitive `VARCHAR UNIQUE`, but ordinary PostgreSQL text uniqueness is case-sensitive. PostgreSQL documents that a normal `UNIQUE` index does not enforce case-insensitive uniqueness; valid choices are a unique `lower(email)` expression index or `citext`. [PostgreSQL `citext`](https://www.postgresql.org/docs/current/citext.html), [indexes on expressions](https://www.postgresql.org/docs/current/indexes-expressional.html).

**RECOMMENDED for Phase B:** store a canonical normalized email and enforce a unique `lower(email)` expression index. This avoids requiring the `citext` extension while keeping a DB-level invariant. Exact normalization and response casing require approval.

### 5.2 Snapshot initialization and revision

**UNKNOWN:** `user_snapshots.payload JSONB NOT NULL` plus `revision DEFAULT 1` does not define an uninitialized account. `{}` is a valid JSON object and cannot safely double as “no imported state”.

**RECOMMENDED for Phase B:** do not create a snapshot row during bootstrap. `GET` returns a typed 404 `state_not_initialized`; first `PUT` requires `expected_revision: 0` and atomically inserts revision 1. Subsequent PUT uses `UPDATE ... WHERE user_id = :user_id AND revision = :expected_revision`, increments revision, and returns 409 when zero rows match. SQLAlchemy documents revision matching as an update predicate and stale write detection. [SQLAlchemy version counters](https://docs.sqlalchemy.org/en/20/orm/versioning.html).

### 5.3 Payload validation and size

- **VERIFIED:** current state is one JSON-compatible object rooted at `version: 2`; dates are serialized as strings.
- **UNKNOWN:** actual maximum export size is not measured. Settings displays a static “184 KB” hint (`apps/web/src/components/SettingsPage.jsx:234-240`), while activity history alone can reach 5000 entries (`apps/web/src/lib/activity.js:25-50`).
- **RECOMMENDED:** require a JSON object, positive supported `schema_version`, `payload.version == schema_version`, and an explicit request/persisted payload limit. The exact limit (recommendation: 5 MiB for v1) is a sign-off item.

## 6. Authentication and HTTP security findings

1. **Password hashing — VERIFIED official guidance:** current FastAPI security guidance uses `pwdlib[argon2]`, `PasswordHash.recommended()`, and a dummy hash for unknown users to reduce enumeration timing differences. [FastAPI password hashing](https://fastapi.tiangolo.com/tutorial/security/oauth2-jwt/). **RECOMMENDED:** opaque DB sessions remain preferable to JWT for this private same-origin app; use pwdlib only for password hashes.
2. **Session token — RECOMMENDED:** generate at least 256 random bits with the Python CSPRNG, store only SHA-256(token), and send the raw token only in the cookie. OWASP recommends CSPRNG-generated opaque IDs, `HttpOnly`, explicit SameSite, Secure, and the `__Host-` prefix in HTTPS production. [OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html).
3. **Cookie dev/prod split — UNKNOWN:** approved production flags are `HttpOnly`, `Secure`, `SameSite=Lax`, but local Vite→HTTP API development needs an explicit non-Secure development policy/cookie name. Production must use a host-only `__Host-...` cookie; development cannot silently inherit weaker production settings.
4. **CSRF — VERIFIED official guidance:** SameSite is defense-in-depth, not a complete origin check; OWASP recommends rejecting unsafe cross-site requests and falling back to exact Origin/Referer verification. [OWASP CSRF Prevention](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html). The Plan's `security/origin.py` is necessary for bootstrap, login, logout, and PUT.
5. **Host/HTTPS — VERIFIED official guidance:** Starlette provides `TrustedHostMiddleware` and `HTTPSRedirectMiddleware`, but reverse-proxy scheme/host handling must be configured consistently. [Starlette middleware](https://www.starlette.io/middleware/). Allowed hosts/origins must be environment-validated, never wildcarded in production.
6. **Bootstrap race — RECOMMENDED:** use one PostgreSQL transaction plus transaction-scoped advisory lock before testing user count and inserting the first user. A count-then-insert without serialization can create multiple first users.
7. **Login brute force — UNKNOWN:** no rate-limit contract exists. Dummy hash equalizes a timing branch but does not rate-limit guessing. Phase B must either add a scoped limiter or explicitly accept the risk until infrastructure rate limiting exists.
8. **Password recovery — VERIFIED scope exclusion:** no reset or admin recovery is planned. Losing the only password can lock the owner out; this operational risk needs explicit acceptance/documentation.

## 9. Risks

| Risk | Severity | Why |
|---|---|---|
| Cross-account state leak | critical | Any request-supplied owner ID or unscoped snapshot query defeats the multi-account goal. |
| Silent stale overwrite | critical | A non-atomic revision check can lose a second device's state. |
| Session theft/CSRF | high | Snapshot contains finance/profile/medication data; cookie flags alone do not replace Origin checks. |
| Ambiguous empty snapshot | high | Batch 3 could overwrite or auto-seed a legitimate `{}` payload. |
| Bootstrap race | high | Two simultaneous requests can create two initial owners without DB serialization. |
| Unbounded JSONB replacement | high | Whole-snapshot PUT can create memory/DB amplification and slow repeated rewrites. |
| Missing login throttling | medium/high | Public login endpoint remains guessable even with Argon2. |
| No password recovery | medium/high | Private owner can permanently lose access without a documented admin path. |
| Frontend `habits` persistence gap | medium | Existing UI habit changes are not part of the snapshot; server storage alone will not fix it. |
| Default Python mismatch | medium | Using 3.14 accidentally can produce a lock/build not representative of target 3.11. |

## 10. Invariants checklist

- **Multi-account isolation:** mandatory; state owner comes only from authenticated session. No API schema accepts `user_id`.
- **Session lookup exception:** resolving the session necessarily starts from `token_hash`, then derives `user_id`; all subsequent user/snapshot operations scope by that derived ID. The original Plan's “every session query receives user_id” wording must be corrected.
- **No silent overwrite:** mandatory atomic expected-revision predicate; 409 on stale revision; no automatic retry.
- **Secrets:** no database URL, bootstrap token, password, raw session token, or snapshot payload in source, frontend, responses beyond intended user fields, or logs.
- **Payload privacy:** do not log request bodies for state/auth routes.
